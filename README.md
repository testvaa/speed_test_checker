# Speed Test Tray

Маленькая утилита для Windows: висит в системном трее и с заданной
периодичностью проверяет скорость интернета через публичный API
спидтеста Cloudflare (тот же, что использует сайт speed.cloudflare.net).
Регистрация и ключи не нужны.

Написана на Go, собирается в один exe без зависимостей.

## Что показывает

Тот же набор метрик, что сводка на speed.cloudflare.net:

- ↓ Загрузка (Мбит/с) и ↑ Отдача (Мбит/с)
- Пинг без нагрузки, а также пинг под нагрузкой при загрузке/отдаче
- Джиттер (вариация задержки)
- Потери пакетов (оценка по мелким пробам)
- IP, IPv4/IPv6, провайдер и AS, город сервера Cloudflare, протокол HTTP

## Мониторинг трафика (постоянный)

Помимо спидтестов, утилита непрерывно следит за всей сетевой активностью
системы (счётчики интерфейсов Windows, локальная петля не учитывается):

- **Сейчас: ↓ … ↑ … Мбит/с** — текущая загрузка/отдача: средняя за
  последние 6 секунд, обновляется каждые 2 секунды; в полном простое
  плавно затухает в ноль;
- **Сегодня: ↓ … ↑ …** — суммарный трафик с начала суток;
- **Ноябрь: ↓ … ↑ …** — суммарный трафик с начала месяца.

Строки видны в меню трея; в tooltip при наведении — текущие скорости,
итог дня и последний результат теста. Накопленные объёмы хранятся в
`traffic.json` рядом с config.json (пишется раз в минуту и при выходе,
хранит ~3 месяца дней и ~2 года месяцев). Трафик собственных проверок
спидтеста тоже попадает в счётчик — как и у любых системных мониторов.

Иконка в трее окрашивается по зонам оценки последней проверки:

| Цвет | Условие (пример для зон 10/50) |
|---|---|
| 🟩 зелёный | загрузка ≥ `good_mbps` (например, выше 50 Мбит/с — хорошо) |
| 🟨 жёлтый | между `bad_mbps` и `good_mbps` (10–50 — норма) |
| 🟥 красный | ниже `bad_mbps` (ниже 10 — плохо) или ошибка проверки |
| ⬜ серый | ещё нет данных |

При наведении на иконку — краткая сводка (скорости, пинг, время).
Полный отчёт — в меню по правому клику. Когда скорость попадает
в «плохую» зону, приходит всплывающее уведомление Windows (повторное —
только после восстановления выше границы «плохо»).

## Веб-дашборд

Вместе с приложением поднимается локальная страница-дашборд:
**http://127.0.0.1:8787** (если порт занят — следующий из 8787–8796;
слушается только 127.0.0.1, наружу не доступна). Открыть можно пунктом
меню трея «🖥 Открыть дашборд».

Что на странице (тёмная тема, стиль «терминала»):

- **шапка** — статус (мониторинг / идёт проверка с фазой и процентами),
  текущая скорость ↓ крупно, ↑ и итог дня;
- **живой график** «Скорость за сессию» — светящаяся белая линия
  загрузки с точечной заливкой и приглушённая синяя отдачи, окно
  ~30 минут; красный пунктир — граница «плохо», красные метки сверху —
  моменты неудачных проверок; во время проверки поверх графика
  появляется панель с фазой и прогресс-баром; в подвале графика —
  **селектор частоты обновления** (1/2/5/10 с, сохраняется между
  открытиями страницы и в config.json);
- **«кто потребляет интернет»** — кнопка в подвале графика открывает
  панель с процессами, у которых есть сетевые соединения: оценка
  активности (байт/с по счётчикам ввода-вывода — диск+сеть, точный
  сетевой счётчик в Windows требует прав администратора), число
  соединений и хосты, к которым они идут (reverse DNS); вкладка
  «Соединения» показывает каждое соединение отдельно: процесс,
  протокол, состояние и удалённый адрес. Данные те же, что у
  `netstat -ano`, права администратора не нужны;
- **аналитика по локациям** — для каждой проверки запоминается, до
  какого сервера Cloudflare она мерилась (город + IATA-код) и через
  какую сеть/AS шёл трафик (видно провайдера VPN):
  - **Рейтинг локаций** — средняя и лучшая ↓, число проверок и пинг
    по каждой локации, отсортировано по средней; клик по строке
    фильтрует историю по локации;
  - **Скорость по часам суток** — 24 столбика средней скорости по
    часам: видно, в какое время суток конкретная локация быстрее;
  - **фильтры** — локация / время суток (ночь-утро-день-вечер) /
    период (сутки, 7 дней, 30 дней, всё); выборка сохраняется между
    открытиями страницы;
- **история проверок** — строки-«штрихкоды» с колонкой локации:
  заполненные тики пропорциональны скорости, цвет — зона
  (зелёный/жёлтый/красный), наведение показывает пинг, джиттер,
  потери, длительность, сервер и сеть; список показывает последние
  10 измерений и раскрывается кнопкой «показать ещё» страницами
  по 10 (смена фильтров сворачивает обратно);
- **трафик** — итоги дня и месяца.
- **темы** — переключатель ☀️/🌙 в правом верхнем углу: тёмная и
  светлая, выбор запоминается (localStorage); перекрашивается всё,
  включая графики на canvas;
- **архив данных** — «⬇ архив» сохраняет историю замеров и трафик
  в один `.jsonl` (по строке на замер), «⬆ импорт» загружает его обратно
  построчно с зелёным прогресс-баром и шагами. Если период архива
  пересекается с существующей историей — вопрос «перезаписать
  совпавшие или пропустить их?». На границе доверия каждая строка
  проверяется (шапка/версия, вменяемые числа, дубли внутри файла,
  лимит 64 МБ). Те же действия доступны ИИ-агенту в чате
  (`export_archive`, `import_archive` с вопросом о пересечении).

Кнопка «▶ Проверить сейчас» на странице запускает проверку так же,
как пункт меню трея. Итоги проверок дописываются в `history.json`
рядом с config.json (хранится до 200 последних; локации есть у записей
начиная с версии 1.4).

## ИИ-агент сети (локальная модель)

На дашборде есть карточка «ИИ-агент сети» с орбом-человечком
(WebGL, глаза следят за курсором; порт движка LiveOrb). Агент
**выключен по умолчанию** и работает целиком на этой машине:

- **«Выводы»** — детерминированный анализ без всякой модели:
  тренд к предыдущим суткам, аномалии (просадки ниже «плохой»
  границы, ошибки), лучшая локация и лучший час за неделю,
  трафик дня/месяца. Виден сразу, без инициализации.
- **«Инициализировать»** (кнопка или клик по орбу) — запускает
  локальный `llama-server` с GGUF-моделью (по умолчанию
  LiquidAI LFM3-1.7B, ~1 ГБ ОЗУ). Через ~минуту орб «оживает»,
  и с агентом можно общаться в чате: он отвечает на русском, опираясь
  только на числовую сводку ваших замеров (выдумывать факты ему
  запрещено промптом). Диалог живёт в памяти сессии; кнопка
  «выключить» останавливает модель. Инструменты агента: замер, настройки,
  экспорт/импорт архива, пинг хоста (`ping_host`) и фоновое наблюдение
  (`watch_host` — «следи за router.local каждые 5 минут»); список
  наблюдений виден в блоке «Наблюдение» на дашборде, переживает
  перезапуск (watch.json) — пинги идут через ICMP без прав администратора.

Пути и GPU настраиваются в config.json:

| Ключ | По умолчанию |
|---|---|
| `agent_llama_server` | `agent\llama-server.exe` |
| `agent_model` | `agent\models\lfm3-1.7b-q4_k_m.gguf` |
| `agent_port` | `8090` (только 127.0.0.1) |
| `agent_device` | `auto` |

Файлы `agent\` в репозиторий не входят (`.gitignore`) — и не нужны:
при первом «Инициализировать» агент сам скачает недостающее, показывая
шаги с процентами: 1) сервер llama.cpp (Vulkan-сборка, ~38 МБ,
GitHub) → 2) модель LFM3-1.7B Q4_K_M (~1 ГБ, HuggingFace) →
3) запуск. Скачивание переживает обрыв (докачка через `.part` +
Range) и отменяется кнопкой «выключить». Нужно ~1,2 ГБ на диске и
интернет только один раз — дальше всё локально. Другую instruct-модель
можно подложить вручную (путь — `agent_model`).

При `agent_device: auto` агент сам ищет NVIDIA среди Vulkan-устройств
(`llama-server --list-devices`): нашли — модель считается на видеокарте
(на GTX 1050 2 ГБ ответ агента занимает ~9 с вместо ~45 с на CPU);
нет NVIDIA — чистый CPU, т.к. iGPU с разделяемой памятью на слабых
машинах обычно медленнее процессора. `agent_device: cpu` форсирует CPU,
конкретное имя (`Vulkan1`) — указанное устройство. На 4 ядрах ~2017
года генерация ≈ 14 ток/с — ответ занимает до минуты, что видно по
статусу «думаю…».

## Использование

Запустить `SpeedTestTray.exe` — появится иконка в трее, первая проверка
выполнится сразу, дальше — по интервалу.

Во время проверки иконка «оживает»: стрелка спидометра делает свип
(иконка становится синей), а в tooltip виден ход проверки — «пинг 40%»,
«загрузка 63%», «отдача 15%», «потери 80%». По завершении приходит
всплывающее уведомление с результатами и цветной иконкой зоны:
«✅ Хорошая скорость», «⚠️ Нормальная скорость» или «🛑 Плохая скорость».

Режим уведомлений выбирается в Настройках:

- **все проверки** — тост после каждого теста (по умолчанию);
- **только проблемы** — только ошибки и «плохая» зона, разово
  до восстановления скорости;
- **выключены** — без уведомлений.

Меню по правому клику разбито на блоки: **📊 ПОСЛЕДНИЙ ТЕСТ**
(результаты спидтеста) и **📶 ТРАФИК** (текущие скорости и накопленные
объёмы), каждая строка — со своей пиктограммой.

- **▶ Проверить сейчас** — первая строка меню;
- **⏳ Интервал** — каждые 1/5/10/15/30/60 минут (сохраняется в конфиг);
- **Настройки** — управление объёмом тестов и зонами оценки прямо из трея:
  - *Трафик за проверку: ≈36 МБ* — подсказка, сколько уйдёт за одну проверку;
  - *Объём загрузки* — 5 / 10 / 25 / 50 / 100 МБ;
  - *Объём отдачи* — 2 / 5 / 10 / 25 / 50 МБ;
  - *Зоны оценки скорости* — две границы вместо одного порога:
    - *Плохо, если ниже* — 3 / 5 / 10 / 15 / 25 Мбит/с (красная иконка
      и уведомление);
    - *Хорошо, если выше* — 25 / 50 / 100 / 250 / 500 Мбит/с (зелёная
      иконка); между границами — «норма», жёлтая иконка.
    - Текущие зоны показаны строкой-подсказкой, например:
      «Красный < 10 • жёлтый 10–50 • зелёный ≥ 50 Мбит/с».
    - Если границы выбраны так, что «плохо» налегает на «хорошо»,
      вторая граница автоматически сдвигается до разумного пресета.
  - *Уведомления* — все проверки / только проблемы / выключены;
- **Выход**.

Все изменения применяются к следующей проверке и сразу сохраняются
в config.json.

Разовая проверка с отчётом в консоль:

```
SpeedTestTray.exe -once
```

Диагностика монитора трафика (16 секунд опросов в консоль):

```
SpeedTestTray.exe -netmon
```

Подробный лог опросов счётчиков — переменная окружения `SPEEDTEST_DEBUG=1`
(пишет `netmon_debug.log` рядом с config.json). Паники фоновых циклов
пишутся в `app_debug.log` автоматически.

## Настройка — config.json

Лежит рядом с exe (если каталог недоступен для записи — в
`%APPDATA%\SpeedTestTray\config.json`). Создаётся автоматически при
первом запуске:

```json
{
  "interval_min": 10,      // период проверок, минут (также меняется из меню)
  "download_mb": 25,       // сколько мегабайт качать в тесте загрузки
  "upload_mb": 10,         // сколько мегабайт отправлять в тесте отдачи
  "latency_probes": 15,    // число проб для пинга/джиттера
  "loss_probes": 100,      // число проб для оценки потерь (0 = выключить)
  "bad_mbps": 10,          // ниже — плохо: красная иконка + уведомление
  "good_mbps": 50,         // выше — хорошо: зелёная; между — норма, жёлтая
  "notify_mode": "all",    // all / problems / off — тосты о завершении
  "timeout_sec": 30        // таймаут каждого этапа проверки
}
```

Изменения подхватываются при следующем запуске (интервал, объёмы и зоны —
сразу из меню «Интервал» / «Настройки»). Значения, заданные в файле, но
отсутствующие в пресетах меню, работают; в меню просто не будет галочки.
Старый параметр `threshold_mbps` мигрирует автоматически
(зелёный ≥ порога, красный < половины).
Учтите расход трафика: одна проверка ≈ `download_mb + upload_mb`
плюс мелкие пробы (по умолчанию ≈ 35 МБ).

## Сборка

Нужен Go 1.21+ (протестировано на Go 1.27):

```
go build -trimpath -ldflags "-s -w -H=windowsgui" -o SpeedTestTray.exe .
```

Флаг `-H=windowsgui` убирает консольное окно (только Windows). Иконки трея
сгенерированы в `icons/` и встроены в exe; перегенерация: `go run ./scripts/genicons`.

## Платформы

| Платформа | Сборка | Примечания |
|---|---|---|
| Windows x64 | локально или CI | полный функционал |
| Linux x64 / arm64 | CI (или `GOOS=linux go build`) | трей: `libayatana-appindicator3-1`; уведомления: `notify-send`; пинг — системный `ping` |
| macOS arm64 (Apple Silicon) | CI | трей и Metal у llama.cpp из коробки; пинг — системный `ping` |
| macOS x64 (Intel) | CI | то же, llama-server на CPU |

- Релизы: тег `v*` запускает `.github/workflows/release.yml` — бинари всех
  платформ прикладываются к релизу автоматически.
- «Кто потребляет интернет» на macOS без sudo показывает меньше процессов
  (ограничения ОС), на Linux — процессы текущего пользователя.
- Мониторинг трафика считает интерфейсы, исключая loopback (`lo`/`lo0`);
  на Linux трафик контейнеров/veth попадает в общий счётчик.

## Заметки

- Тест загрузки/отдачи использует одно соединение (как «честная»
  пропускная способность). Сайт Cloudflare местами использует несколько
  параллельных соединений, поэтому его пиковые цифры могут быть выше.
- «Потери пакетов» — оценка на уровне HTTP-проб, а не ICMP; при
  блокировке ICMP в сети это надёжнее пинга, но это приближение.
- Большие объёмы теста (свыше 25 МБ) качаются последовательными кусками
  по 25 МБ: Cloudflare отклоняет одиночные запросы «на сотню мегабайт»
  (HTTP 403 и «получено всего 1 байт»).
- Если этап не уложился в `timeout_sec`, тест не падает: скорость
  считается по фактически переданному объёму и помечается «(обрезан)».
- Если уведомления не появляются — проверьте, что для PowerShell
  разрешены уведомления в настройках Windows (Система → Уведомления).

## Структура

```
main.go        — точка входа, планировщик, режим -once
measure.go     — замеры через speed.cloudflare.com
config.go      — конфиг с дефолтами
trayui.go      — меню/иконка/tooltip/уведомления
netmon.go      — постоянный монитор трафика (traffic.json)
dashboard.go   — локальный веб-дашборд (127.0.0.1:8787, history.json)
dashboard.html — страница дашборда, встраивается в exe
site/          — исходники лендинга (React + Tailwind + Vite)
docs/          — собранный лендинг для GitHub Pages
icons/         — встроенные иконки трея
scripts/genicons — генератор иконок
```

## Лендинг (site/)

Исходники страницы проекта — React + Tailwind CSS v4 + Vite:

```bash
cd site
npm install
npm run dev      # локальная разработка
npm run build    # сборка в ../docs (для GitHub Pages)
```

Сборка идёт с `base: /speed_test_checker/` — под URL проекта
`https://testvaa.github.io/speed_test_checker/`. В `docs/` лежит
собранный результат (коммитится). Проект настроен под shadcn/ui
(`components.json`, алиас `@/`) — компоненты из shadcn и Magic MCP
добавляются через `npx shadcn add <component>`.
